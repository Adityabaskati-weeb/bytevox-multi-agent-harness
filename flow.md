# ByteVox Harness Execution Flow

This page follows the current code paths. The CLI entry point is [`__main__.py`](src/bytevox_harness/__main__.py), which calls [`cli.py::main()`](src/bytevox_harness/cli.py). Core orchestration is in [`harness.py`](src/bytevox_harness/harness.py); providers, tools, limits, traces, and evaluation live in their own modules.

## Command dispatch

`cli.py::build_parser()` defines `run`, `compare`, `hotpotqa-compare`, `demo`, `failure-demo`, `limit-demo`, `show`, and `replay`. `cli.py::main()` handles `show` and `replay` first. Other commands resolve the run folder; output is restricted to the project tree.

| Command | Path after argument parsing |
|---|---|
| `run` | Resolve optional cap → `cli.py::_provider()` → build `Limits` → `Harness(...).run(task)` → print result metadata. `--mode` selects `multi` (default) or `single`. |
| `compare` | Resolve optional cap and provider plus positive `--repeats N` (default `1`) → `benchmark.py::run_comparison()` → alternate multi/single order per task across repetitions → evaluate each run and write `6 × N` trial rows plus grouped medians/ranges. |
| `hotpotqa-compare` | `hotpotqa.py::load_hotpotqa_dev_distractor()` reads the required local JSON file and records `--source-url` (defaulting to the official CMU URL) with its file hash → prepare the legacy sample or seeded proportional stratified sample (`--sample-seed`) under `runs/hotpotqa-corpora/` → resolve provider, response format, cap, and configured HotpotQA limits (`--max-tokens` default 16,000; `--max-agent-tokens` default 6,000; `--max-agent-seconds` default 32; overall run limit remains 60 seconds) → `benchmark.py::run_hotpotqa_comparison()` applies `equal-run-envelope-v1`, keeps those per-agent caps for multi-agent, and sets the single-agent per-agent step/time/token caps to the shared run caps → run paired trials → score answer, citation-support, and retrieval-support metrics after each `Harness.run()` → write separate `hotpotqa-benchmark.{md,csv,json}` files. |
| `demo` | Run the same paired comparison flow as `compare`, then run a deterministic offline prompt-injection example and the offline failure demonstrations. |
| `failure-demo` | `cli.py::_run_failure_demo()` runs a persistent worker-timeout scenario and a checker-repair scenario using the offline provider. |
| `limit-demo` | Construct a multi-agent run with a deliberately small step limit. |
| `show` | Resolve an in-folder `.md` path with `cli.py::_trace_path()` and print the report. |
| `replay` | Resolve an in-folder `.jsonl` path and pass it to `cli.py::_replay()`. `--all` prints full event records. |

For `run`, `compare`, `hotpotqa-compare`, and `demo`, `cli.py::_provider()` calls `providers.py::provider_from_args()`. Offline is selected by default. A non-local OpenAI-compatible endpoint passes through `cli.py::_approve_if_remote()` and requires the explicit flag and interactive `APPROVE` confirmation before a model request. `--max-cost-usd` overrides `BYTEVOX_MAX_COST_USD`; the CLI validates it as finite and non-negative.

On `run`, `compare`, `hotpotqa-compare`, or `demo`, `--source-scope-candidate` selects prompt variant `d73` for the requested run/comparison arm; otherwise `d54` remains selected. The CLI passes the variant into the applicable `Harness`; the manifest records it and `prompts.py::system_prompt()` applies its actor/entity scope guidance to every model role. D73 changes no schemas, tools, budgets, or scoring, and is available only with the OpenAI-compatible provider because the offline provider does not implement prompt variants. In `demo`, the comparison uses the selected variant, while its offline injection/failure scenarios keep their established prompts.

## HotpotQA local-data and scoring path

The `hotpotqa-compare` command never fetches data. `hotpotqa.py::load_hotpotqa_dev_distractor()` validates the caller-provided dev distractor JSON, records its source-file SHA-256 and provenance, and records the user-supplied `--source-url` or official CMU URL by default. The source URL must be a public HTTPS URL without embedded credentials, query, or fragment. Without `--sample-seed`, it selects the first comparison and bridge cases followed by source-order fill (or the first record for a one-case sample); with a seed, it uses proportional Hamilton allocation by question type and deterministic within-type sampling. It then writes one Markdown evidence file per context sentence. Each generated evidence ID maps to its source `(title, sent_id)` in a `HotpotQAScoringRecord`; the model-facing corpus and question do not carry the answer/support label fields. Per-case corpus paths use a hash of the dataset record ID and generated corpus content, independent of sample ordinal, and a fingerprint check rejects stale or missing evidence files. `CorpusTools` precomputes BM25 term frequencies and document frequency, boosts complete title matches, and uses a Unicode-aware tokenizer with stopword filtering that preserves short entity tokens such as `Ed`, `US`, and `AI`.

`benchmark.py::run_hotpotqa_comparison()` gives multi and single modes the identical raw question and a fixed, generic three-facet contract with `summary_first_line_prefix: "Answer: "` and `summary_first_line_max_words: 8`. The format rule is separate from the user question, so it does not enter corpus search text. Gold values are not used to build facets, payloads, prompts, runtime validation, trace events, or manifests. After `Harness.run()` returns and its trace has a terminal `run_finished` event, `score_hotpotqa()` parses the first answer line and maps citations to source fact tuples. `score_retrieval_support_recall()` independently collects unique IDs returned by `search_documents` in the closed trace and compares them with scorer-held support IDs; `read_evidence` and model citations do not count as retrieval. The benchmark computes answer EM/F1, citation support P/R/F1/EM, retrieval support recall, and joint metrics. Post-run metric summaries are appended to the report; run rows and dataset provenance go only to the separate `hotpotqa-benchmark.md`, `.csv`, and `.json` artifacts. The per-task corpus hash is compared with the manifest hash after every trial.

The benchmark policy is scoped to HotpotQA evaluation; generic `Harness` defaults and ordinary `run`/`compare` limits are unchanged. A single `single_agent` identity otherwise accumulates the per-agent cap across all of its model calls, while multi-agent has separate role identities. To give both benchmark arms the same run-level envelope, only the baseline's per-agent step, time, and token caps are raised to the run caps; its per-request `max_completion_tokens` is also raised to the existing lead cap to match multi-agent synthesis/planning requests. Effective caps are recorded in each run manifest and report and in the aggregate report metadata/table. The completed [D91 three-task × one-repeat follow-up](runs/current-source-d90-3x2-20261017/equal-budget-followup.md) used the $0.06 estimated aggregate guard and the CLI's typed remote approval. It found joint F1 tied at 0.667; multi-agent completed 2/3 versus 3/3 and had higher measured latency and token-derived cost. The D91 report documents the partial multi-agent run and remaining per-call/topology differences; this small sample supports no superiority or equivalence claim.

This path is a small pilot over a locally supplied public dev sample. It does not establish general model quality or avoid possible pretraining exposure; an offline provider exercises the adapter and evaluator mechanics only.

## Harness initialization and shared run lifecycle

`Harness.__init__()` in `harness.py` validates a requested remote cost guard before any request. A requested remote cap requires both per-million-token rate variables; without a cap, rates are optional and only determine whether API cost can be reported. It resolves the input folder, constrains report/trace writes to the project tree, then creates a `RunBudget`, `TraceWriter`, and `CorpusTools` instance. A configured cap is enforced only for remote providers; local/offline runs are left unchanged. The cap is per Harness run: default `compare` makes six provider-backed runs, `compare --repeats N` makes `6 × N`, and the benchmark portion of `demo` makes six. Thus a configured per-run estimate `C` can reserve up to `6 × N × C` across a repeated comparison, plus possible estimate overage.

`Harness.run()` first writes a timestamped `.manifest.json` sidecar with run/task identity, harness and Python versions, source/prompt/corpus hashes, model label, sampling temperature and response format, endpoint scheme plus a local/remote placeholder and SHA-256 endpoint fingerprint, limits, supplied contract, and cost configuration. The fingerprint distinguishes normalized endpoint identities without storing host, path, query, credentials, or key material. It then writes `run_started` with the initial manifest plus provider/model, mode, corpus label, tool policy, and any estimated cost guard. The run dispatches to `_run_multi()` or `_run_single()`; `_plan()` or `_run_single()` resolves the effective validation contract and updates the sidecar, and `run_manifest_updated` records that final manifest in the trace. The manifest is a configuration fingerprint, not a replay package for a hosted model. Budget exceptions and other run errors preserve `_last_draft` when it has supported claims, record the error, and set the run partial. Worker failures, checker rejection, missing explicit task coverage or contract format, budget exhaustion, and reported cost overage also lead to a partial result. The final result is rendered to Markdown, included in `run_finished`, and returned to the CLI.

## Multi-agent path

1. `Harness._plan()` in `harness.py` asks `CorpusTools.list_documents()` for the inventory and calls read-only `CorpusTools.search_documents()` with the raw question for at most five seed results. It passes those as `seed_evidence` with an explicit untrusted-data notice. The lead prompt asks for three distinct, complementary facets and allows a dependent follow-up query that uses an entity discovered in seed evidence. An ad-hoc run lets the lead create the validation facets; `normalize_validation_contract()` accepts valid three-facet output or uses `fallback_validation_contract()`. Criteria for required evidence IDs and terms are accepted only from a trusted harness caller; planner output cannot add hard evaluator gates. The benchmark passes task facets only. Its gold evidence IDs and terms remain in the evaluator and are not serialized as reference labels in the model payloads, run contract, manifest, or trace. Ordinary corpus results and cited IDs still appear in tool messages and output. Each facet is mapped by index to one of the three fixed worker IDs, with bounded query/goal strings. The runtime contract and structured plan are traced.

   `make_validation_contract()` treats caller-supplied evidence IDs as opaque keys and preserves their exact characters, repeated spaces, and full length. It still normalizes and caps the natural-language facets and required terms. The D81 `CorpusTools` regression constructs an ID from a long heading and a filename with repeated spaces, then verifies that both contract creation and trusted normalization retain it unchanged. The bounded checker/reviser regression also verifies exact preservation through `Harness` construction, the checker payload, the reviser payload, and the reviser's allowed-ID JSON Schema enum.
2. `_run_workers_parallel()` starts up to three workers with separate fixed deadlines and cancellation events. `_run_worker()` uses a valid planner-generated specialist query alone; only a missing or invalid query falls back to the original task plus that specialist's goal. The evidence finder and gap auditor search at most five results. The independent corroborator searches at most five unless its inventory has repeated sentence-shard filenames with the same `doc-NN` and title suffix. For such a group, it retrieves up to eight and compares the actual serialized five-result/full-inventory and eight-result/compacted provider requests with the normal estimate. It sends eight results and the representative inventory only when that request estimate is no larger; otherwise its model payload uses the first five results and full inventory. Inventories without a same-source group and other specialist roles stay at five. The full inventory and all retrieved evidence remain in trace, handoff, and shared `WorkerResult` state. The model-facing inventory is labeled as representative and non-exhaustive when compacted. The worker model payload keeps the full task, goal, matching `focus`, query, evidence, and an untrusted-content notice. Worker prompts treat those planner fields only as untrusted scope/search hints; command-like text in them cannot override the original task or harness safety rules. Its output shape comes from the worker role's fixed JSON Schema and prompt; it does not repeat the three-facet validation contract. The contract and tool allowlist remain in the structured assignment trace, and the lead/review stages retain the full runtime contract and any final-answer format rules. The risk worker may reread one top hit. `WorkerResult` retains retrieved records and the structured goal/query/focus on success, model failure, or coordinator-created timeout. `WorkerControl` publishes the records before provider I/O so the coordinator can also retain them when it creates a worker-timeout result. Completed results are kept even if a sibling times out; failed workers make the run partial.
   The scheduler emits `agent_timeout` at a worker deadline and cancels that worker's retry path. It waits for an already-running provider call to return before synthesis and final artifact writes. The built-in HTTP provider receives the remaining worker time as its request timeout. Python cannot forcibly stop a custom provider that ignores `timeout`, so such a provider can delay the caller after the deadline; a bounded fake-provider test exercises this exact behavior.
3. `_synthesize()` interleaves specialists by retrieval rank in fixed role order, adds the lead's top-five raw-question seed results, and merges duplicate IDs while retaining every supplying agent in `source_agents`. It marks evidence IDs cited by a successful specialist, but treats those claims only as leads. Before filling the bounded eight-record pool, it reserves each evidence-producing worker role's first valid evidence ID and the first planner-seed ID absent from all worker results. Remaining slots go first to other specialist-cited IDs, then to other planner seed hits, then to other worker evidence, preserving the rank of each source within its fill group. Each evidence `text` remains limited to 1,200 characters including the visible `… [truncated]` marker. The exact ID, `text_truncated`, supplying agents, and citing specialist IDs remain inspectable. The synthesis handoff carries every worker's goal/query/focus and status, plus successful claims; failed workers keep their assignment and any retrieved evidence. The planner seed and worker records carry the same untrusted-corpus notice. Synthesis, checker, and reviser payloads each carry an untrusted-data notice and a short contract-source enum. Planner-generated assignments and planner/fallback facet wording are treated as untrusted hints or coverage labels; caller-supplied criteria and output-format rules remain authoritative. Prompts require synthesis and review to verify proposed facts against the actual source text and to check each multi-hop link separately. Strict claim schemas restrict IDs to evidence in that provider call. `_check()` starts with the bounded evidence in `evidence_by_id` and rereads only cited or required IDs absent from that map; `_revise()` receives the merged map and its strict schema restricts citations to those IDs. If a call supplies no evidence, its strict schema permits a summary with zero claims instead of emitting an empty ID enum.

   `RunBudget.begin_step()` estimates the request representation returned by `Harness._model_request()`. For the OpenAI-compatible provider, that representation comes from `OpenAICompatibleProvider.build_request_envelope()` and contains the selected model, temperature, messages, response format, and dynamic evidence-ID JSON Schema. The same builder creates the HTTP JSON body; the sender adds `max_tokens` after the budget reserves the completion cap separately. The API key is added only as an HTTP header and never enters the envelope or trace. Offline runs keep the prior role/instructions/payload estimate. All estimates remain a character-based approximation (about one token per four characters), not provider token counts, and do not model tokenizer or HTTP protocol overhead. Eight excerpt texts can contribute up to 9,600 characters (roughly 2,400 estimated input tokens before titles, provenance, claims, instructions, and other fields). The existing HotpotQA limits remain 6,000 estimated tokens per agent and 16,000 per run. The cap bounds payload size but does not guarantee a model call fits; a large payload can stop a stage. Before synthesis, `_run_multi()` saves supported specialist claims as `_last_draft` so a later budget stop can preserve them.
4. `_check()` initializes available evidence from retained synthesis records and rereads cited or required IDs that are absent. It prepares a candidate map of at most eight records (each text at most 1,200 characters), prioritizing explicit required IDs, draft citations, specialist-cited records, records matching trusted required terms, then other retrieved alternatives. Hard validation uses all available retained/read-back evidence. The checker request normally receives draft-cited IDs, explicit required IDs, specialist-cited records, and term-support candidates from the bounded pool; if a claimless draft has no selected IDs but evidence exists, it receives one candidate. Specialist citation metadata is only a navigation hint, never proof. An unresolved citation after readback makes the checker receive the full bounded pool to diagnose the unknown ID. A resolved citation omitted by the cap creates a hard issue that prevents acceptance. The harness returns the bounded candidate map to `_revise()` for alternative citations. More than eight explicit required IDs creates an explicit hard failure because all criteria cannot fit in the evidence cap. The checker request's smaller evidence map is recorded in the review trace; the `checker_result` event also records the candidate IDs. That event keeps the combined top-level `accepted`/`issues` result and separately records the model decision/findings in `llm_review` and hard-check outcome/findings in `deterministic_validation`; compact `replay` renders the two sources separately. An `accepted: true` response with any non-empty `issues` list is rejected as a checker inconsistency and recorded in deterministic validation; valid model acceptance requires `issues: []`. Harness code independently rejects malformed/empty claims, missing or unresolved IDs, missing explicit required evidence IDs or terms, and a summary line that misses its prefix or exceeds its trusted word limit. The loop in `_run_multi_after_workers()` allows one revision via `_revise()` and one subsequent check; a final rejection marks the result partial.

### D45 implementation and controlled evaluation

This local code iteration responds to v7's high overlap among specialist retrieval sets and a trace where the reviewer lacked source text for a missing answer-chain link. It changes worker searches to use a valid planner query without automatically appending the full question; the raw-question top-five seed remains with the lead, and the old anchored query is used only when a planner query is missing or invalid. Each specialist receives the full task, goal, matching focus, query, evidence, untrusted-data notice, and fixed worker response schema. Worker prompts treat planner-produced assignment fields as untrusted hints, never instructions. The full validation contract and any caller-supplied final-answer format rules stay with the lead and review stages. A short source enum tells review prompts whether facets came from a caller or the planner/fallback; planner/fallback facets are coverage labels, while caller-supplied criteria and format rules remain authoritative. The structured `{goal, query, focus}` assignment travels through `WorkerResult` and synthesis. Synthesis reserves one first valid evidence ID per evidence-producing role, then fills remaining slots with specialist-cited IDs and other ranked IDs, within the existing eight-record, 1,200-character limits. The prompts explicitly require source-text verification; no result is inferred from a specialist citation alone.

The review follow-up has 45 passing local tests; all three deterministic offline multi fixtures completed at 11,229/12,000, 10,568/12,000, and 11,180/12,000 estimated tokens. The D45 candidate was then measured in the one-repeat public-data A/B described below. These results are descriptive; no causal or generalizable model-quality claim follows from one repeat.

### D47 caller-supplied answer-prefix normalization

It leaves claims, evidence IDs, and later summary lines untouched. The existing first-line word limit and multi-agent source/citation checker still run afterward. Planner/fallback contracts are excluded. In the D47 holdout, the event appeared on four code-on outputs and the two normalized multi-agent drafts were accepted by the checker. ### D50 answer-slot prompt guidance

`prompts.py::system_prompt()` appends the same short final-answer instruction for `lead_synthesizer`, `lead_reviser`, and `single_agent`. It asks these roles to answer the requested slot in a narrow source-supported phrase, preserve material identity or edition qualifiers, omit first-line framing, and state a directly shared category for commonality questions. The instruction adds no task-specific examples or labels. It is prompt guidance; it does not enforce semantic answer matching in harness code. A focused regression covers the three recipients and confirms it is absent from planner, worker, and checker prompts.

### D53 citation-contract clarification and evaluation

`prompts.py::system_prompt()` gives the synthesizer, reviser, and solo role the same citation convention: factual citations belong in `claims[].evidence_ids`, and the concise `summary` follows from those claims. The checker role is told to validate each claim against its cited source and require inline citations in the summary only when the original caller requested that format. The matching short rules in `harness.py::CONTRACT_RULES` keep this distinction in the persisted contract. These prompt changes address the D52 trace pattern where checker rejections interpreted a citation-free summary line as unsupported despite citations on the structured claims; they do not skip claim verification or allow unsupported facts. ### D56 experiment runner and artifact flow

The isolated D56 experiment lives under `runs/hotpotqa-d56-evidence-chain-ab/`; it does not alter the active harness prompt. `prepare_d56.py` loads the local public HotpotQA dev-distractor file, applies the prior-ID exclusion set, selects a type-stratified sample using question text and type only, builds per-question evidence corpora, freezes control/candidate source snapshots, and writes `campaign-plan.json`, `schedule.csv`, and sample provenance. Answer and supporting-fact labels remain in scorer records, separate from the model-facing task and generic validation contract.

`run_d56_campaign.py` verifies the frozen snapshots and plan before remote calls, waits for the explicit remote approval gate, then walks the randomized schedule. For each slot it selects a dedicated control or candidate package/provider instance, constructs a `Harness` with the same corpus, generic contract, model, and limits, and calls `Harness.run()`. After the run closes, the runner scores the answer and retrieval trace, checks the manifest corpus hash, writes the linked trace/report/manifest paths and metrics to `run-rows.jsonl`, and updates `campaign-status.json`. After all rows are present, it calculates the paired hierarchical bootstrap and promotion gates, then writes `campaign-summary.json` and `.md`.

## Tools and untrusted corpus text

`CorpusTools` in `tools.py` walks corpus entries in sorted depth-first `Path` order without materializing the full `rglob()` result. It stops with a clear error above 50,000 filesystem entries, 10,000 eligible `.md`/`.txt` files, 8 MiB of aggregate raw file text, 10,000 non-empty evidence sections, or 250,000 indexed tokens across body, title, section, and document fields; these caps exceed the saved HotpotQA corpus sizes observed for this project. The existing per-file behavior remains: files over 128 KB and paths resolving outside the corpus root are skipped. Real directories are traversed, directory symlinks are not followed, and file symlinks are accepted only when their resolved targets stay inside the corpus root. Exceeding a new corpus-wide limit raises an error instead of returning a silently partial evidence set. An eligible in-root `.md` or `.txt` file that cannot be read also raises a clear error rather than being silently omitted. File contents must be valid UTF-8; decoding is strict and strips an optional leading UTF-8 BOM before Markdown parsing. An invalid sequence raises `ValueError` with the relative path and byte offset, instead of introducing replacement characters into evidence. Text line boundaries and section bodies are processed incrementally after decoding each capped file, avoiding a list of all lines or all section fragments. The token cap bounds the total term occurrences retained by BM25 Counters, including title and path metadata; token/index memory can still exceed raw text size because Python stores per-term objects. Markdown `##` sections become evidence IDs such as `operations#delay-causes`. Unique sections retain the legacy `basename#heading-slug` ID; a collision gets a relative-path ID, with a deterministic occurrence suffix when repeated normalized headings share a document. This keeps nested same-stem files, duplicate headings, and Unicode headings addressable while preserving all unique fixture IDs. It precomputes BM25 term frequencies and document frequencies with title/section/path field weights, length normalization, Unicode-aware tokenization, stopword filtering, and short-entity preservation. Search returns at most 15 results. The stable worker IDs map to task-general profiles: `worker_causes` is the evidence finder (search only), `worker_outcomes` is the independent corroborator (list names and search), and `worker_risks` is the gap-and-caveat auditor (search and reread evidence). The corroborator receives the local document-name inventory as untrusted routing metadata, and the trace records each specialist profile and allowlist. The assigned planner facet still controls what each worker investigates. The lead may list documents and search the planning seed; the checker may reread; and the solo baseline may use all three tools. Each tool call passes the allowlist check and budget accounting before returning a result. `_finish_tool()` traces the result and scans it for known instruction-injection patterns; matches remain corpus data and produce `untrusted_content_detected`. The benchmark's full evidence view is an internal evaluator method, not an agent tool.

`CorpusTools.read_evidence()` matches the exact ID returned by search against the already-loaded corpus; it does not clip identifiers at 160 characters. Valid headings or relative document paths can make an ID longer than that. The regression in `tests/test_regressions.py::test_read_evidence_accepts_long_ids_returned_by_search` verifies that an ID over 160 characters still retrieves the same evidence text.

## Provider calls, retries, and cost reservations

`Harness._model_call()` obtains the budget/trace input from `_model_request()`, reserves a run/agent step and estimated input tokens through `RunBudget.begin_step()`, then—when a remote cap is active—calls `_reserve_provider_cost()` before provider I/O. For OpenAI-compatible requests, `_model_request()` uses `OpenAICompatibleProvider.build_request_envelope()`; `generate_json()` uses the same builder for the HTTP body and adds the separately reserved completion cap. Dynamic response schemas and their evidence-ID enums are included in both representations. The API key is added only as an HTTP header and never enters the representation or trace. Offline providers retain the earlier role/instructions/payload estimate. The estimate is character-based and approximate, not a provider-token measurement; historical model-run traces and benchmark totals predate this change and were not recomputed. A single `_cost_lock` protects the spend/reservation ledger across parallel worker calls. The request timeout is bounded by the 15-second provider ceiling, remaining run time, and remaining agent or worker time. `ROLE_TOOLS` permissions are enforced by harness code; corpus lookups run before model calls, and their results are included in the payload. Tool names stay in structured handoff trace events but are omitted from model prompts and payloads because this adapter does not expose callable functions. The prompt states that the model call has no callable functions and must return JSON in normal message content. For multi-hop answers, the shared prompt asks roles to separate supported evidence links into claims and cite every source sentence used for each claim. `RunBudget.begin_step()` reserves up to 1,536 completion tokens for lead planning and synthesis, and 1,024 for other roles; the trace records each effective per-call cap.

The OpenAI-compatible adapter permits HTTP only for localhost/loopback; remote endpoints require HTTPS. Redirects must stay on the configured origin and cannot weaken transport. The adapter never logs its API key.

The offline provider implements deterministic responses in `providers.py::OfflineProvider.generate_json()`. `OpenAICompatibleProvider.generate_json()` sends JSON chat-completion requests through the standard-library HTTP client and validates reported prompt/completion token counts when present. `--response-format json_object` keeps broad compatibility; `json_schema` sends the role's strict schema for providers that support it. `parse_chat_completion()` distinguishes empty content, truncation, refusal, unsupported tool calls, text content blocks, malformed JSON, and non-object output; `validate_role_response()` then checks semantic role fields. When a received completion fails protocol parsing, refusal, or content filtering, the adapter raises a typed usage-carrying error. `Harness._model_call()` records validated tokens and known cost before retrying, and the `model_error` trace preserves `protocol_parse`, `refusal`, or `content_filter` as the provider error category. Missing or invalid usage stays unknown and retains the conservative estimate; transport errors or a response envelope that is not valid JSON cannot provide validated usage. Malformed or rejected output becomes a handled error/partial result if retries do not recover, with the terminal report and trace still written. `_invoke_with_retry()` allows one bounded retry with backoff. A preflight failure releases its cost reservation because no request began; ambiguous provider exceptions retain the estimate because the remote outcome may be unknown. Successful calls record input/output tokens and known per-call cost on `model_result` even without a cap. Rates are optional for cost reporting; a requested remote cap requires both rates. On successful responses, reported cost settles the reservation; missing or malformed usage retains the estimate. Any ambiguous remote request marks provider token totals and `_cost_usage_known` unavailable, so `_cost_usd()` reports the whole run's API cost as unavailable even if other requests reported usage. With a cap, successful-call costs also remain in `cost_settled` events. Missing usage or an ambiguous request marks total actual spend unknown and retains the conservative estimate. If actual reported cost exceeds its estimate, a `cost_settled` trace event flags review, and `Harness.run()` marks the result partial. The estimate guard can block later requests, but parallel calls already in flight may still finish. This estimate is not a guaranteed billing limit.

`RunBudget` in `budget.py` enforces overall and per-agent step, token-estimate, and time limits. Regular commands retain the 20-second per-agent default; only `hotpotqa-compare` exposes `--max-agent-seconds`, defaulting to 32 seconds while keeping the 60-second overall run ceiling. This gives the pilot retry headroom around the 15-second provider timeout and short backoff, without establishing model quality or guaranteeing a retry will complete. Provider requests have a bounded timeout and token completion cap. Tool calls also count toward the step budget. The budget snapshot is attached to the result/report. Remote API cost is calculated from usage and rates when possible; missing rates or usage remain unavailable. Localhost cost is reported as $0. Offline token estimates are mechanics accounting, not API token usage.

## Trace and report output

`TraceWriter` in `trace.py` serializes each JSONL event under a lock with sequence, UTC timestamp, elapsed milliseconds, run ID, event type, and event fields. `finish()` writes the terminal `run_finished` record and closes the writer against late appends. `Harness._render_report()` writes the corresponding Markdown answer with status, contract, citations, errors, budgets, provider/model/response format, cost, and cap details. Benchmark evaluation appends fixture scores or post-run answer, citation-support, and retrieval-support metrics to the per-run report. A cost-estimate overage has an explicit report section and partial status. The timestamped manifest sidecar, report, and trace are saved under `runs/` by default.

`cli.py::_trace_path()` resolves reads within the configured runs folder. `cli.py::_replay()` displays the trace timeline; `--all` prints complete JSON records. Both replay modes route text through `_write_stdout_safely()` so characters unsupported by a narrow console encoding do not crash the command. Unsupported display characters are replaced in terminal output only; stored traces remain UTF-8. Neither `show` nor `replay` reruns an agent or provider.

## Paired comparison and scoring

`benchmark.py::SAMPLE_TASKS` defines three fixed tasks, scorer-only gold evidence IDs and terms, and three task-specific facets. `run_comparison()` builds a runtime validation contract from the facets alone, then repeats each task `N` times (positive integer; default `1`) and alternates each task's mode order between multi-then-single and single-then-multi. Each trial gets a fresh `Harness` with the same provider instance, corpus, limits, and task contract. `evaluate()` receives the gold labels only after `Harness.run()` returns. There are `6 × N` runs total; at five repeats this is 30 harness runs. The cost cap applies to each Harness run independently.

The saved comparison table links to post-D22 artifacts. Older run files with non-empty hard criteria are retained for history and are not evaluation evidence; `runs/README.md` records how to identify them.

`evaluate()` emits a narrow `fixture_score`: 50% gold evidence-ID coverage, 25% citation ID validity, and 25% gold-term presence in a cited claim and its source. ID validity only checks whether an ID exists; term matching does not judge meaning or entailment. Summary-only terms do not count. The evaluator uses the gold labels only after the answer is complete; the runtime checker reviews source support and task relevance without receiving the gold reference lists. For general tasks without explicit criteria, task relevance remains a checker/model judgment. Evaluation records provider/model, repetition, run status/partial flag, token usage, API cost, cap snapshot, exact evidence IDs, key-term matches, and report/trace/manifest filenames. Each benchmark summary row links to the per-run JSONL trace, Markdown report, and manifest; the report contains the score breakdown next to the answer and citations. `write_comparison()` keeps one row per trial in `benchmark.json` and `.csv`, and its Markdown report adds per-task/mode completion counts and median/range for fixture score, wall time, and known API cost. Partial runs remain visible and are included in score/time summaries; unknown API cost is excluded and counted as unavailable. An ambiguous remote request marks full-run cost and token totals unavailable even if other calls reported usage; successful calls still show per-call usage and known cost on `model_result`. Offline output is labeled as a mechanics benchmark, not model quality. The five-repeat fixture comparison demonstrates harness mechanics only. A separate configured-model HotpotQA pilot is now recorded in `runs/hotpotqa-hf-gpt-oss-20b-deepinfra-final-v3/hotpotqa-benchmark.md` (local archive, omitted from curated package: `runs/hotpotqa-hf-gpt-oss-20b-deepinfra-final-v3/hotpotqa-benchmark.md`); its tiny sample and partial failures do not establish a multi-agent quality advantage. The README's configured-model fixture example uses five repeats.

### D64 opt-in checker-budget path

`cli.py` passes `run --checker-budget-recovery` into `Harness`; the flag is false by default and is recorded in the manifest only when enabled. After `_run_multi()` saves the merged specialist claims in `_last_draft`, `_synthesize()` builds the bounded evidence pool through `_build_synthesis_context()` and shares that same pool with the normal synthesis, `_check()`, and the preflight. `_checker_evidence_map()` and `_project_checker_context()` build the checker evidence map and exact compact model payload without corpus reads; fallback eligibility requires every preserved-draft citation and explicit required evidence ID to exist in the bounded pool and remain in the projected checker payload.

`_checker_budget_preflight()` builds the projected normal checker payload from `_last_draft` with the same compact evidence projector used by `_check()`. It first checks only the first synthesis request plus the first full-cap checker request. If these fit, synthesis runs even when the checker retry reserve would not fit. Only if this first normal pass cannot fit does preflight compare the retry-safe compact checker sequence (two full-cap attempts by default) against current run/agent token and step budgets. When that fallback sequence fits and all citations/required evidence are available, it emits `checker_budget_fallback`, returns the preserved draft, and routes it to the ordinary checker and deterministic validation. If neither plan fits, normal synthesis proceeds; with the opt-in enabled, `RunBudget.begin_step()` rejects any checker reservation that would provide less than the full configured completion cap, so the normal run exception handler returns a partial result before provider I/O. The regular retry and one-revision flow still applies. This is an estimated, unvalidated candidate: it cannot forecast provider latency or tokenizer differences, and a later retry/revision may still exhaust the remaining budget.
