# ByteVox Harness Decision Log

This is a practical record of the choices reflected in the current code. Status distinguishes work added in the current implementation from architecture retained from the starter harness and deliberate scope cuts.

## Context

ByteVox's assignment calls for an inspectable multi-agent document-analysis demo. The harness therefore focuses on answering questions from a small, local evidence corpus, while making agent inputs, evidence citations, limits, failures, and model usage reviewable. `decision.md` records the decisions; [flow.md](flow.md) follows the current execution path.

## Decisions

### D1 — Keep the document-analysis task as the product scope

**Status:** Implemented.

The assignment is demonstrated with local document analysis. A public code-repository review was considered as a possible demo target, but it would replace the assignment's core use case rather than improve it. The corpus is fictional and local so citations and untrusted-document handling can be inspected without web retrieval.

### D2 — Use a small Python standard-library runtime with an offline default

**Status:** Retained baseline.

Keep standard-library threading and HTTP and avoid an agent framework or runtime dependencies. `offline-deterministic` remains the default so orchestration can be inspected repeatably without credentials or network access. The optional OpenAI-compatible provider enables model-backed runs when explicitly selected. This keeps setup small, at the cost of a deliberately simple local search and provider abstraction.

### D3 — Keep the corpus boundary local, read-only, and role-scoped

**Status:** Retained baseline.

Agents receive only the corpus tools allowed for their role, enforced by [`tools.py`](src/bytevox_harness/tools.py). Corpus content is treated as untrusted data and suspicious instruction patterns are logged. No agent receives shell, network, environment-variable, or write tools. This makes the demo's authority boundary narrow and reviewable; broader computer use and live retrieval are intentionally out of scope.

### D4 — Keep three worker identities, but make their evidence facets task-adaptive

**Status:** Implemented.

The harness retains the three specialist IDs (`worker_causes`, `worker_outcomes`, and `worker_risks`) for compatibility with existing schemas, fixtures, and traces, but the IDs no longer define the research topic. They map to task-general profiles: evidence finder, independent corroborator, and gap-and-caveat auditor. The lead plans exactly three task-relevant evidence facets, and each facet remains the assigned worker's topic. Permissions are distinct and read-only: evidence finder can search; corroborator can list document names and search; auditor can search and reread retrieved evidence. The contract aligns each facet with one worker while preserving the maximum fan-out of three.

### D5 — Create a compact validation contract before specialist work

**Status:** Implemented.

Ad-hoc multi-agent runs use the lead's three facets, with a harness-owned generic fallback when model output is missing or malformed. The contract also carries fixed citation, untrusted-data, and uncertainty rules. It is saved in the trace and report and passed to the lead, synthesizer, checker, and reviser. Since D45, each worker model call gets the original task and its assigned goal/focus instead of repeating the full three-facet contract; the structured assignment trace still records the contract. This keeps workers focused and avoids repeating contract text while the lead and reviewer retain the full contract. Reviewer payloads also carry a short source enum: caller-supplied contracts remain authoritative, while planner/fallback facet text is treated only as coverage labels and cannot carry instructions. The harness owns the rules so model output cannot weaken them.

For benchmark tasks, the evaluator supplies a curated task-specific contract to both modes. This keeps the single-agent and multi-agent comparison on the same task criteria without adding a planner call to the solo baseline. The benchmark's scoring rubric and expected facts remain evaluator-authored and separate from that contract.

### D6 — Preserve a direct single-agent baseline

**Status:** Retained baseline and aligned with the new contract.

The solo mode receives one prepared prompt with corpus results, then answers directly. It uses the supplied benchmark contract, or a generic fallback for ad-hoc runs. It does not make an additional lead-planner call and does not run the multi-agent checker/revision loop. This keeps the baseline simple and avoids charging it for planning stages it does not need.

### D7 — Bound orchestration and retain useful partial work

**Status:** Retained baseline; worker cancellation refined.

Keep run and per-agent step, token-estimate, and time limits; one retry; and one checker revision. Each specialist now has its own fixed deadline and cancellation event so a timeout does not cancel a sibling. Completed worker results and supported draft claims are retained when a later worker or stage fails. The result is marked partial when required work stops or the checker rejects the final draft.

### D8 — Support paired model-backed comparisons without changing the default

**Status:** Implemented over the retained optional provider.

`compare` and the benchmark portion of `demo` use the same configured provider/model, corpus, task contract, read-only tool boundary, and evaluator rubric for each multi/single pair. The role-specific allowlists remain in force within each mode. Offline remains the default and is labeled as a mechanics check, not model quality. Remote endpoints require the existing interactive approval path; API keys are loaded by environment-variable name and are not placed in prompts or traces.

### D9 — Add an estimated remote USD guard with conservative reservations

**Status:** Implemented in the latest change.

`--max-cost-usd` or `BYTEVOX_MAX_COST_USD` configures a per-Harness-run estimate guard. Remote cost calculation uses provider-reported token usage and configured `BYTEVOX_INPUT_USD_PER_1M` and `BYTEVOX_OUTPUT_USD_PER_1M` rates. Rates are optional without a cap; usage is still recorded when cost is unavailable. A requested remote cap requires finite, non-negative rates before any request is sent. Before each request, the harness atomically reserves estimated input-token cost plus the request's maximum completion cost; successful reported usage settles the reservation. A reservation is released only when the request has not started. Failed or usage-ambiguous calls retain their estimate conservatively.

This is not a guaranteed billing cap: provider tokenization and billing can differ from local estimates. If reported cost exceeds its reservation, the trace records the overage and the run becomes partial/reviewable; in-flight parallel requests can still finish. Successful calls record input/output tokens and known per-call cost on `model_result` even when no cap is enabled. The cap applies per task/mode run: default `compare` has six runs, while `compare --repeats N` has `6 × N`; the benchmark portion of `demo` has six provider-backed runs. A provider-side hard limit remains the only external billing control this generic adapter cannot set.

### D10 — Keep the trace as the inspectable run record

**Status:** Retained baseline.

Each run writes an append-only JSONL event trace, a Markdown report, and a timestamped secret-safe manifest sidecar. The trace records messages, tool calls/results, model calls/errors/retries, budget events, validation contract, and terminal result; it also embeds the manifest at `run_started`. `replay` reads it without rerunning the model. The trace supports audit and explanation, not resumption; persistent checkpoints and run continuation were cut.

### D11 — Keep benchmark claims narrow and link every score to evidence

**Status:** Retained benchmark design; documentation updated.

Three fixture tasks use explicit expected evidence IDs, expected terms, and a narrow fixture score: 50% expected-ID coverage, 25% citation ID validity, and 25% cited-claim/source term presence. Citation ID validity checks only whether each cited ID exists; neither this nor term presence establishes entailment. Localhost API cost is $0; remote cost is reported only when usage is complete and rates are available. Any ambiguous remote request makes full-run API cost unavailable. Successful-call usage and known cost remain on per-call trace events; with a cap, valid successful usage settles the reservation, while missing usage or an ambiguous request marks total actual spend unknown and retains the conservative estimate. Every comparison row links to the run report, trace, and manifest, which connect the score to the answer and run configuration. The current five-repeat fixture artifact demonstrates harness mechanics only. A separate configured-model HotpotQA pilot has now run; its small sample and partial failures do not establish a multi-agent quality advantage. See `runs/hotpotqa-hf-gpt-oss-20b-deepinfra-final-v3/hotpotqa-benchmark.md`.

### D12 — Keep the multi-agent topology as planned parallel fan-out

**Status:** Confirmed after comparing alternatives; no implementation change.

To apply the `principle-exhaust-the-design-space` rule, three distinct topology sketches were compared against ByteVox's requirements and the existing code:

| Candidate sketch | Strengths | Costs and risks | Fit |
|---|---|---|---|
| **A. Planned parallel fan-out (selected):** `lead plan → 3 independent specialist facets in parallel → lead synthesis → checker → at most 1 revision` | Uses parallelism for independent evidence gathering; gives each specialist a bounded, inspectable assignment; isolates a worker timeout; directly exercises structured handoffs, shared trace, limits, and checker rejection. | Requires a synthesis step and can spend more model calls than the solo baseline. | Strongest fit for the assignment and current document-analysis task. This is the current implementation. |
| **B. Sequential pipeline:** `lead → specialist 1 → specialist 2 → specialist 3 → synthesis/check` | Later specialists can build on earlier findings; easy to express dependencies between steps. | Serial latency; one failure delays all later work; weaker demonstration of parallel execution for independent document facets. | Useful for genuinely dependent tasks, but a poorer default for this task. The assignment names a second pattern as optional. |
| **C. Shared blackboard with dynamic workers:** `lead posts jobs → workers claim/update shared state → coordinator closes work → checker` | Can adapt the number and order of workers to a task; natural fit for long-running or open-ended work. | Needs job ownership, synchronization, conflict resolution, completion rules, and more complex traces; harder to explain and finish reliably within the 4–5 hour scope. | Adds infrastructure without improving this small, fixed-corpus demo enough to justify it. |

**Decision:** Keep A as the sole multi-agent orchestration pattern. Retain the direct single-agent mode as the required comparison baseline, not as a second multi-agent topology. The lead may adapt the three evidence facets to the user's task, while the worker slots and their permissions remain fixed. Add a second topology only if a future task has dependent stages and enough evaluation time to show that it improves quality, time, or cost.

**Reason:** A covers the required lead planning, three specialists, structured handoffs, parallel execution, inspectable state, bounded retries, partial failure, and checker loop with the least additional machinery. It also makes the demo flow and trace easier to explain. B remains a viable task-specific alternative; C is not justified by the assignment's scope.

**Design reference:** [principle-exhaust-the-design-space](https://github.com/cursor/plugins/blob/main/pstack/skills/principle-exhaust-the-design-space/SKILL.md) asks for multiple materially different sketches and a side-by-side comparison before choosing when an architectural decision lacks a clear precedent.

### D13 — Add optional alternating benchmark repetitions

**Status:** Implemented.

`compare --repeats N` runs each fixture task in N multi/single pairs, alternating which mode runs first across repetitions. The default is one repetition so `compare` does not incur surprise model cost; the configured-model README workflow explicitly opts into five repetitions. Every trial remains a separate JSON/CSV row with its repetition number and report/trace links. The Markdown summary reports completion counts and median/range for score and wall time, plus median/range over known API costs.

The cap is applied per Harness run, so N repetitions may produce up to `6 × N` provider-backed runs. The summary includes partial trials in score/time statistics and shows completed counts; unknown API costs are excluded from cost statistics and counted as unavailable. Alternating order helps make order effects visible while keeping the comparison schedule simple.

### D14 — Do not report an untracked project-duration estimate

**Status:** Applied in the README.

The README records AI use and the evidence-backed checker-budget mistake. No project-wide time figure is included because the user said it was not needed and the project-wide time was not tracked.

### D15 — Mark full-run remote cost unavailable after an ambiguous call

**Status:** Implemented and smoke-verified.

A remote request can fail after the provider has received it, so previously reported successful-call usage may be only a lower bound. When any remote request has an uncertain outcome, `Harness._cost_usd()` and the run's provider-token totals return unavailable. Successful per-call usage/cost remains on each `model_result`; when a cap is enabled and usage is valid, settled costs also appear in `cost_settled` trace events. Missing usage or an ambiguous request marks total actual spend unknown and keeps the conservative reservation committed. This avoids presenting an incomplete subtotal as total cost or token usage.

### D16 — Name the citation score for what it measures

**Status:** Implemented in benchmark output and documentation.

The evaluator checks whether cited evidence IDs exist in the loaded corpus; it does not establish that the cited text entails the associated claim. The score and report field are therefore named `citation_id_validity`, with matching table/report wording and an explicit limitation. This keeps the benchmark from implying semantic citation verification it does not perform.

### D17 — Require secure remote transport and validate model response shapes

The OpenAI-compatible adapter accepts HTTP only for localhost or loopback IPs; remote endpoints must use HTTPS, and redirects must stay on the configured origin without weakening transport. Provider JSON is validated against each role's expected top-level and nested fields after usage accounting, so malformed claims become errors/partial runs while the harness still writes a terminal report and trace.

### D18 — Make fixture task coverage explicit and name scores narrowly

At this stage, benchmark validation contracts carried trusted task expected evidence IDs and key terms, and the harness applied those criteria before accepting a run. This addressed missed fixture coverage but exposed the gold labels to the agents, so this benchmark use was later superseded by D22. The benchmark field is named `fixture_score`: it uses evidence-ID coverage, ID existence, and case-insensitive term presence in a cited claim and source, so it does not establish semantic correctness or general model quality. For ad-hoc tasks without explicit criteria, task relevance remains a checker/model judgment.

### D19 — Save a secret-safe run manifest beside each report and trace

Each run writes a timestamped manifest with harness/Python versions, prompt and corpus hashes, limits, mode, model label, sampling temperature, validation contract, and cost configuration. For planner-generated contracts, the sidecar is updated once the contract resolves; a `run_manifest_updated` event records that final version in the trace. The endpoint is represented by its transport, a local/remote placeholder, and a SHA-256 fingerprint of normalized scheme, host, port, and path; raw host/path/query/userinfo and API key material are not stored. The trace keeps the initial manifest at `run_started` and the resolved manifest update, linking each benchmark row's score and metrics to its run config and evidence artifacts. These fingerprints and hashes identify inputs but are not a complete replay package: matching source, corpus, endpoint configuration, and hosted model behavior may not be available later.

### D20 — Keep worker deadline handling cooperative and race-free

Each worker passes its remaining deadline to the built-in HTTP adapter. The executor waits for running workers before report/trace finalization so late responses cannot race budget snapshots or terminal artifacts. Python cannot forcibly stop an arbitrary custom provider that ignores its timeout; such a provider can delay the caller after the deadline, and the harness reports the worker timeout once the deadline passes. A bounded fake-provider test exercises that event.

### D21 — Record resolved run configuration, including local model temperature

The manifest now records the adapter's effective temperature for local and remote OpenAI-compatible endpoints. After a planner or solo path resolves its validation contract, the harness updates the sidecar and appends a `run_manifest_updated` trace event. This makes ad-hoc run configuration inspectable while preserving the initial `run_started` record. A manifest remains a configuration fingerprint; it cannot freeze a hosted model alias or recreate server-side behavior.

### D22 — Keep benchmark gold labels outside model inputs

The fixture benchmark previously included expected evidence IDs and terms in the validation contract sent to agents. That made the score easier to satisfy but contaminated any model-backed quality comparison. `run_comparison()` now builds the runtime contract from task facets only; `gold_evidence_ids` and `gold_terms` are used by `evaluate()` after `Harness.run()` returns. Regression tests inspect provider validation-contract payloads, current manifests and traces, and a sentinel task that confirms reference labels appear only in post-run score artifacts. The score breakdown remains in the post-run report for inspection. D22 supersedes D18's benchmark use of hard gold criteria; the harness still supports trusted criteria for explicit non-benchmark callers. Historical files produced before D22 are retained, identified in `runs/README.md`, and excluded from evaluation evidence.

### D23 — Add a local-data HotpotQA public-data pilot

**Status:** Implemented, offline-verified, and exercised in a three-example configured-model pilot. The pilot is operational evidence, not a generalizable quality comparison.

Use the official HotpotQA dev distractor split as a small public-data pilot for document evidence analysis. Require the user to supply the downloaded JSON path locally; the dataset loader does not fetch or vendor the dataset. Record the source URL (defaulting to the official CMU file but overridable for a mirror), version, split, CC BY-SA 4.0 license, exact local-file hash, deterministic sample selection, and aggregate/per-task corpus hashes with the separate `hotpotqa-benchmark` artifacts. The 61 MB Hugging Face mirror is a valid local source option; the first three sampled rows were checked against official Hugging Face validation rows, but its byte hash differs from the CMU file, so its provenance must name the mirror. For three examples, choose the first `comparison`, then first `bridge`, then fill from source order; for one example, keep the first source record. Sentence-level evidence files preserve a mapping from generated IDs to HotpotQA `(title, sent_id)`. Per-case paths use hashed record identity plus generated corpus content instead of sample ordinals, so loading a different sample size cannot reuse another record's directory; the loader verifies the exact file-set hash. Search indexes both the complete original title and the title slug in its path.

Keep answer and support labels in scorer-only task records. Give both modes the identical question-format instruction and generic facets, then call the evaluator only after `Harness.run()` returns. Ask for `Answer: <short answer>` on the first summary line so normalized answer EM/F1 does not compare an explanatory paragraph against a short reference. Report parse failure, answer EM/F1, support-fact P/R/F1/EM, joint EM/F1, latency, known provider tokens, and known API cost. Do not replace the earlier fixture `benchmark.*` artifacts.

**Reason and limits:** A public labeled task set supports quality checks beyond the deterministic fixture, while sentence IDs make citation support measurable. The pilot is intentionally tiny and drawn from public dev data, so it can be affected by model pretraining exposure and is not a generalizable quality claim. The configured GPT-OSS pilot produced 3 completed and 3 partial trials; mean answer EM/F1 was 0.333 in both modes, with mean support F1 0.318 for multi-agent and 0.324 for single-agent. The multi-agent median was 42.699 seconds versus 14.555 seconds for single-agent. These summaries include partial runs and do not support a claim that multi-agent is better. Known single-agent API cost totals $0.00050885 across two runs; the other four runs have unknown usage/cost because of ambiguous remote requests. See `runs/hotpotqa-hf-gpt-oss-20b-deepinfra-final-v3/hotpotqa-benchmark.md`.

### D24 — Make the remote tool boundary explicit in model prompts

**Status:** Implemented; exercised by the configured-model pilot. Provider calls returned ordinary JSON on some paths, while timeouts and malformed content still caused partial runs.

The first Hugging Face pilot passed all six requests to the selected endpoint, but all six harness runs were partial. Trace evidence showed empty model message content, and a replay of a failed specialist prompt produced a Groq error indicating that GPT-OSS tried to call `search_documents` even though the adapter supplies no callable-tool schema. The harness had already run the allowlisted corpus lookup and included its results in the model payload.

Change `prompts.py::COMMON` and `system_prompt()` to say that tool permissions are enforced by the harness, their results are already in the request, and the model must return JSON in ordinary message content without issuing tool calls. Keep the existing `ROLE_TOOLS` checks and corpus tools unchanged.

**Reason:** The old phrase “Available tools” conflicted with the actual OpenAI-compatible request shape and encouraged models that support native tool calls to emit a call the adapter cannot execute. The prompt now matches the implemented control flow without broadening agent permissions. The final pilot traces show valid regular-content responses from some roles and no callable-function schema; no model-call payload includes the corpus tool names. The harness itself still records local read-only tool operations separately from model calls. Refer to the pilot's per-run traces, and do not use partial failures as model quality wins.

### D25 — Keep the HotpotQA answer format inside the required summary field

**Status:** Implemented; answer-line parsing succeeded on 4 of 6 configured-model trials. Two trials failed to produce a parseable answer.

The first Qwen/NScale run returned JSON with a top-level `Answer` key and `claims` but no `summary`; the harness trace then recorded validation errors such as `lead_synthesizer response summary must be a non-empty string`. The task instruction had asked for an “Answer” on the first summary line without explicitly saying that this text belonged inside the JSON `summary` property.

Change the HotpotQA task format instruction and its documentation to require `summary` to begin with `Answer: <short answer>`, forbid a separate top-level `Answer` key, and keep evidence-backed statements in `claims`.

**Reason:** The scorer parses the answer from `RunResult.answer.summary`, and every provider role uses that fixed structured response shape. Naming the exact JSON field preserves the common harness contract while still giving the HotpotQA answer normalizer its expected first-line text. The prompt yielded parseable first answer lines in 4/6 trials, but two malformed/empty outputs remain visible in the report and traces.

### D26 — Allow bounded remote requests enough time to finish

**Status:** Implemented; bounded timeouts and a retry were observed in the configured-model traces. Some requests still timed out.

The first Qwen/NScale run's lead planner used both allowed attempts and each ended at the hard-coded five-second HTTP timeout, before any specialist dispatch. The single-agent path completed in about five seconds, confirming the cap was too tight for the hosted route. Keep the existing 20-second per-agent and 60-second whole-run deadlines, but raise the individual provider request ceiling to 10 seconds. The remaining agent/worker and run deadlines still take precedence, and the one-retry limit is unchanged.

**Reason:** The old ceiling caused an avoidable multi-agent failure before orchestration began. Ten seconds provides additional provider latency headroom while retaining bounded waits and graceful timeout handling. Traces show the configured timeout and one-retry behavior; the pilot also confirms the remaining time limit can still produce partial results when the hosted model is slow.

### D27 — Keep harness tool names out of provider inputs

**Status:** Implemented and trace-inspected in the configured-model pilot.

After D24 clarified that model calls cannot execute functions, the GPT-OSS route still attempted `search_documents`; Groq's response identified that attempted function call. A later Qwen run also showed the named allowlist in the model-call prompt, even though lookup results had already been fetched by the harness. The capability names in the prompt and payload were unnecessary for the requested JSON response and continued to prime native tool-call behavior.

Remove allowlist names from the provider system prompt and task payloads. Keep the role-to-tool allowlists in `ROLE_TOOLS`, enforce them in `CorpusTools`, and retain them in structured handoff trace events. Continue telling models that the request has no callable functions and that they must use supplied evidence only.

**Reason:** The tool boundary must be both enforced by code and accurately described to a model. Omitting tool names from model inputs closes the gap that remained after a verbal no-call instruction, without expanding access or removing traceability. Inspection of all six run traces found no corpus-tool names in serialized provider model-call inputs; harness-originated read-only tool events remain separately visible.

### D28 — Reserve a larger response cap for lead planning and synthesis

**Status:** Implemented and observed in configured-model traces; lead calls used the 1,536-token cap, with a lower cap possible when remaining budget requires it.

The GPT-OSS lead-planner request returned `finish_reason=length` at the harness's 768-token completion cap, leaving incomplete JSON. Replaying the same label-free planner payload with a 1,536-token cap returned valid JSON in about 7.7 seconds, within the existing 20-second per-agent deadline. The harness now reserves up to 1,536 completion tokens for `lead_planner` and `lead_synthesizer`, while other roles remain at 768. The effective cap is written to model-call traces and both caps appear in budget snapshots/manifests.

**Reason:** The two lead roles emit larger structured plans and merged answers. A per-role cap gives them room to finish valid JSON without increasing every worker's token reservation. The overall and per-agent token/time budgets and one-retry limit still apply. The final pilot confirms this larger cap does not by itself prevent malformed responses or provider timeouts.

### D29 — Keep the HotpotQA answer line short and exact

**Status:** Implemented; the configured-model scorer parsed the required answer line in 4/6 trials, while 2/6 outputs were unparseable.

Completed GPT-OSS single-agent runs returned a parseable answer line, but it contained explanation after the short answer (for example, `No, we cannot confirm ...`), producing zero answer EM/F1 on the pilot example. The prompt now requires the first line of the JSON `summary` to be exactly `Answer: <short answer>`, with no explanation on that line; the explanation and cited claims belong below it. Gold answers remain scorer-only.

**Reason:** The answer metric compares the normalized short answer, while the support metric separately checks cited evidence. A concise first line gives the scorer the intended answer without giving the model any gold label. This pilot confirms the format can be parsed but does not demonstrate reliable answer or support quality.

### D30 — Raise the non-lead completion cap to 1,024 tokens

**Status:** Implemented and verified in the final paired provider pilot. Non-lead model-call traces record a cap of up to 1,024 tokens; a call can be clamped lower by remaining run/agent budget.

A replay of the exact GPT-OSS single-agent prompt at the previous 768-token cap ended with truncated JSON. Replaying it with a 1,024-token completion cap returned schema-valid JSON using 994 completion tokens in 8.37 seconds. Keep the lead planner and synthesizer cap at 1,536 tokens, and raise the cap for other roles from 768 to 1,024. Both values remain bounded by run and per-agent budgets and are recorded in traces and manifests.

**Reason:** The observed valid response establishes that 768 tokens was too small for this task's structured solo response. A 1,024-token cap gives that response room to complete without raising the lead-role cap or removing the enclosing budget limits.

### D31 — Give the public HotpotQA pilot a bounded retry budget

**Status:** Implemented and verified in the final paired provider pilot. All six manifests record 16,000 run tokens and 6,000 per-agent tokens; three runs remained partial after provider errors/timeouts.

The earlier HotpotQA run budget of 12,000 estimated tokens per run and 4,000 per agent left little room for a retry after accounting for the worker prompt and evidence. Give `hotpotqa-compare` defaults of 16,000 run tokens and 6,000 tokens per agent, while retaining 12,000 and 4,000 for the regular run and fixture comparison commands. Keep both HotpotQA values overrideable through `--max-tokens` and `--max-agent-tokens`; the effective limits are recorded in each manifest. The retry count, per-agent deadline, provider timeout, and per-run cost estimate cap remain unchanged.

**Reason:** The change gives the existing single-retry policy bounded output headroom on the public-data pilot while retaining the harness's time, step, token, and cost controls. It is limited to the pilot command so regular harness defaults do not silently increase.

### D32 — Add opt-in role-specific strict JSON Schema output

**Status:** Implemented; 24 local regression tests pass. Endpoint acceptance of the strict schema remains to be verified by the reviewed one-example smoke. `json_object` remains the default. `--response-format json_schema` sends a strict schema for each known role, with every object property required and additional properties disabled. The selected response mode is recorded in the manifest and report. The parser reports empty content, provider refusal, tool-call attempts, truncation, malformed JSON, and non-object responses separately; it accepts text content blocks and does not log API keys.

**Reason:** The prior model-backed runs showed malformed or truncated role JSON. A provider-supported schema can constrain response shape at generation time while an opt-in preserves compatibility with endpoints that do not support strict structured outputs. The semantic validators remain active after parsing.

### D33 — Replace token overlap with title-aware BM25 and preserve short entities

**Status:** Implemented and locally verified by the 24-test suite and a separate 50-case, no-model retrieval diagnostic. `CorpusTools` precomputes field term frequencies and document frequency, then ranks with BM25 using body, title, section, and path weights. Its Unicode-aware tokenizer removes common stopwords but retains short entity tokens such as `Ed`, `US`, and `AI`. Search returns at most 15 items; specialists still retrieve five each and the single baseline can retrieve 15.

**Reason:** On the first 50 HotpotQA dev-distractor source indices, the implemented ranker improved same-query support recall@15 from 0.7377 for token overlap to 0.9143 for BM25 (+0.1767 before rounding). The sample, source hash, and protocol are recorded in `retrieval-diagnostic.md` (local archive, omitted from curated package: `runs/hotpotqa-retrieval-diagnostic-v4/retrieval-diagnostic.md`). This measures whether gold evidence can be retrieved, not whether an LLM answers correctly. The long-title case also showed that filtering all tokens of length two or less dropped `Ed` from `Ed Wood`. The local implementation adds no package dependency and keeps retrieval deterministic.

### D34 — Keep the raw question in search and anchor specialist queries

**Status:** Implemented and locally verified by the 24-test suite. HotpotQA task strings now contain only the original question. The shared trusted validation contract carries `summary_first_line_prefix: "Answer: "`, and harness validation checks that prefix. Each specialist search combines the original question with the lead's facet query so the planner cannot remove the question's named entities.

**Reason:** The previous answer-format instructions were appended to the task and therefore entered retrieval text. Planner queries such as `Compare nationalities` also lost entity terms, reducing retrieval relevance. The output-format rule is not a gold label and remains identical for both comparison modes.

### D35 — Add seeded proportional sampling and scorer-only retrieval recall

**Status:** Implemented and locally verified by the 24-test suite. `--sample-seed` enables deterministic proportional stratification by HotpotQA type while no-seed selection preserves the original ordering. After `Harness.run()` closes the trace, the evaluator reads only `search_documents` results to compute retrieval support recall, separate from the cited-support metric. The selected seed and selection rule are included in dataset provenance.

**Reason:** A reproducible seeded sample supports larger follow-up evaluations without changing the legacy three-case pilot. Retrieval recall distinguishes a missing support sentence from a model that retrieved the sentence but did not cite it; post-run trace scoring keeps support labels out of the prompt, tools, contract, and manifest.

### D36 — Use the reachable strict-schema route and record the v4 smoke evidence

**Status:** The one-example `json_schema` smoke was run on two Hugging Face provider routes. The Groq route returned HTTP 403 for both paired calls; both runs were partial and token use/cost were unknown. The NScale route (`openai/gpt-oss-120b:nscale`) accepted the schema and completed both calls, with $0.00242850 total known API cost. On this one case, multi-agent answer F1 was 0.000 and retrieval support recall was 0.667; single-agent answer F1 was 0.154 and retrieval support recall was 1.000. Full outputs are preserved in the Groq smoke (local archive, omitted from curated package: `runs/hotpotqa-hf-gpt-oss-120b-groq-v4-smoke/hotpotqa-benchmark.md`) and NScale smoke (local archive, omitted from curated package: `runs/hotpotqa-hf-gpt-oss-120b-nscale-v4-smoke/hotpotqa-benchmark.md`) folders. ### D45 — Preserve specialist retrieval intent and source leads through review

**Status:** Implemented and locally verified, then measured in the controlled one-repeat D45 A/B recorded in D46. Focused regressions cover direct specialist-query search, anchored fallback for invalid queries, task-specific goal/focus/query in worker requests, assignment preservation for successful and failed workers, role reservation and specialist-citation priority inside the synthesis cap, checker visibility of specialist-cited evidence, worker contract isolation, and the planner-output trust boundary. **Evidence and reason:** V7 traces show substantial overlap among the three workers' five-result retrieval sets, and task `hotpotqa-0026` shows a missing relation chain after synthesis/review even though specialists had found useful evidence. The existing runtime appended the raw user question to every valid planner query, which repeatedly biased BM25 toward the same top records. The model handoff also discarded goal/query/focus and the eight-record pool was filled only by rank, so source records named by specialist claims could be left out before synthesis or checking. These trace findings motivate a narrow retrieval and handoff change; they do not show that the change improves model quality.

**Decision:** Keep the raw-question top-five seed lookup with the lead so it can find entity anchors. For a valid planner query, use that query alone for the worker search; use the original task plus task-specific goal only when the planner query is missing or invalid. Keep the full original task in every worker model payload, and include both the task-specific goal and its matching focus plus query. Worker requests also retain supplied evidence, an untrusted-content notice, and their fixed JSON response schema and prompt; explicitly treat planner-generated goal/focus/query as untrusted scope/search hints, never instructions. The full task contract is not repeated in worker inputs. The lead, synthesizer, checker, and reviser retain the full contract. Reviewer payloads add only a short contract-source enum: planner/fallback facets are coverage labels and command-like text in them is ignored; caller-supplied criteria and output-format requirements remain authoritative. Store the structured `{goal, query, focus}` assignment in `WorkerResult` for normal completion, model error, and coordinator timeout, and include assignment/status in synthesis input. Keep specialist claims as untrusted leads: prompts instruct the synthesizer and checker to verify each proposed fact against supplied source text and check individual multi-hop links. Within the unchanged eight-record, 1,200-character synthesis bound, first reserve one valid evidence ID for each evidence-producing role, deduplicating shared IDs while retaining provenance; fill the remaining slots with successful-specialist-cited IDs, then other ranked IDs. **Trade-offs and evaluation protocol:** A valid but overly broad or entity-poor planner query can retrieve less useful records now that the full question is not appended. Role reservation can displace later cited evidence when all roles produce records; remaining slots still prioritize cited IDs, and citations remain leads rather than entailment judgments. The implementation preserves existing evidence/text/token limits and the single-agent baseline. The D46 controlled comparison uses the same task IDs, model, schema, and budgets but only one repeat. Its measured changes cannot be separated from sampling/model variability; use the run as descriptive evidence and require repeated runs before making a broader quality claim.

### D65 — Bound corpus traversal and text ingestion

**Decision:** Replace `sorted(root.rglob("*"))`, which materializes the whole path list, with a sorted depth-first `os.scandir()` walk whose pending paths and each directory listing are bounded by a 50,000-entry cap. Also cap eligible `.md`/`.txt` files at 10,000, aggregate ingested raw text at 8 MiB, non-empty evidence sections at 10,000, and the total BM25 index at 250,000 token occurrences across body, title, section, and document fields. The index cap addresses the fact that one `Counter` per evidence field can use substantially more memory than raw text. File lines are yielded incrementally and each section body is assembled as it is read, avoiding a full line list and per-section fragment list. Files larger than the existing 128 KB per-file threshold remain skipped, and symlink files are still accepted only when their resolved targets stay within the corpus root; symlink directories are not traversed. Corpus-wide cap violations raise clear errors rather than returning a partial evidence set. Sorting uses the platform `Path` order so evidence IDs and ordering stay stable.

**Evidence and verification:** The saved HotpotQA inventory measured a maximum of 1,337 eligible `.md`/`.txt` files, 227,314 bytes, and 23,769 body tokens across 41 corpus copies. The 10,000-file cap is roughly 7.5× the file maximum, the 8 MiB aggregate-text cap roughly 36× the byte maximum, and the 250,000-token cap roughly 10× the observed body token count; runtime token accounting also includes metadata fields. The 50,000-entry traversal cap and 10,000-section cap leave headroom while limiting traversal state and retained index records. Focused tests cover a small sorted corpus (including the existing oversized-file skip), exact normalization across many lines and line-boundary styles, file/aggregate/entry/section/token cap failures, and the existing fixture ID set. No full suite, model call, or quality benchmark was run; this resource-bound change makes no model-quality claim.
